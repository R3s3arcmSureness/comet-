## 0. 输入前置条件（★ 版本 1.1 新增，最关键的契约）

> **上游（逆向工具链）必须完成「脱壳 / 解混淆 / 解密」，送入本服务的是明文。**

### 0.1 `consent_scope` 判别器（★ v1.2 新增，强烈建议采纳）

> **问题**：当栈帧 API 名未收录、payload 键名也不可读，且信号字段被改名时，
> 「真·无个人数据」与「信号字段被改名（契约违约）」两种输入**在当前契约下信息论上不可区分**。
> 无法区分 ⇒ 只能二选一：要么把违约输入误判为合规（**漏判 26.68%**，实测），
> 要么把真 NONE 也一律送人工（人工率 +1.08%，且随非 PII 流量占比线性放大）。

> **解法**：要求**所有**调用（含无个人数据的）都携带 `consent_scope`：

| `consent_scope` | 语义 | 服务行为 |
|---|---|---|
| **缺失** | 上游未按 v1.2 实现 → 契约违约 | `needs_review=true`（`contract_missing_consent_scope`） |
| `[]`（空数组） | 上游**显式声明**本次调用不涉及个人信息 | 可自动判 `NONE||COMPLIANT` |
| `["TYPE", ...]` | 本次调用声明采集的数据类型 | 作为 Tier5 恢复数据类型；仍 `needs_review=true` |
| 含非法值（非 14 类之一） | 契约违约 / 新增未登记类型 | `needs_review=true`（`contract_unknown_scope_value`） |

- 服务侧开关：`PC_SCOPE_CONTRACT`（**默认 `1`，即契约模式已生效**；显式设 `0` 可退回旧行为）。
  默认值的变更依据：核桃编程真实日志（6,364 条）实测——`0`（旧行为）漏判 **558 条**（占敏感 24.12%），
  `1` 漏判 **0**；代价是无 `consent_scope` 的输入一律转人工。见 `reports/真实日志评估_最终结论.md`。
- **上游成本**：非 PII 调用也带一个空数组。
- **收益**：人工率保持基线不变，同时消除上述"不可区分"缺口，漏判率归零。
- 实测（OOD n=10000）：默认 1.16% 人工 / 0 漏判；v1.2 未适配 2.24% / 0；
  **v1.2 已适配 1.16% / 0**；违约输入 100% / 0。

- 送入口径 = 「**明文 JAVA 调用堆栈 + 明文传参**」，即：字符串常量已解密、编码已还原、控制流已去平坦化。
- **判定服务不对混淆负责**：混淆处理在 L2 哨兵（`deobfuscate.input_guard`）做**质量校验**——
  - 干净明文 → 放行；低危残留（零宽/同形字）→ 确定性还原；高危残留（`sf:`/`b64:`/高熵串）→ **强制复核**。
- ⚠️ **标识符部分混淆（已支持，v1.1 实现）**：上游尽量还原语义名，但**部分标识符无法完全解混淆**。
  判定服务对栈帧做**分级识别**（`rules_engine._resolve_data_type`），按可靠性降序：

  | Tier | 条件 | 结果 | 是否复核 |
  |---|---|---|---|
  | 1 `full` | 完整 API token 可匹配（`LocationManager.getLastKnownLocation`） | 高置信判定 | **否**（信号齐全时，唯一可自动判 COMPLIANT 的层） |
  | 2 `class` | 类名可读、方法名混淆（`LocationManager.a`） | 定位数据类型 | **是**（`partial_identifier`） |
  | 3 `method` | 方法名可读、类名混淆（`a.b.getLastKnownLocation`） | 定位数据类型 | **是**（`partial_identifier`） |
  | 4 `payload` | 前三级失败，回退 payload 键名（`phone`/`contacts`…） | 定位数据类型 | **是**（`indirect_tier:payload`） |
  | 5 `consent` | 前四级失败，回退 `consent_scope` 里的类型名（多类型取最高风险） | 定位数据类型 | **是**（`indirect_tier:consent`） |
  | — | 全混淆（`a.a.b`）+ 无 payload / scope 线索 | **不判** | **是**（`obfuscated_identifier_unresolved`） |

  **红线 1（fail-closed）**：识别不出数据类型时，**绝不落 `NONE||COMPLIANT`**——
  - 栈帧无混淆痕迹**且**无敏感 API**且** `params` 中无任何信号字段 → 才判 `NONE||COMPLIANT`（真·无个人数据）
  - 栈帧有混淆痕迹（短标识符 `a.a.b`）→ 一律 `needs_review=true`，交人工
  - 契约建议：若上游拥有 mapping 表（`mapping.txt`），随输入提供可显著降低复核率。

  **红线 2（INV-1′，2026-10-07 新增）**：**只有 `tier ∈ {full, none_verified}` 才允许输出 `COMPLIANT`**。
  任何间接识别层（Tier2–5）即使算出"合规"，也必须降级为 `needs_review=true`——
  因为类型是推断出来的，真实类型可能不同，而类型不同则违规结论不同（例如
  `consent_scope=["PHONE"]` 但实际采集 `ID_CARD`，应为 `NO_CONSENT`，按 `PHONE` 算却得 `COMPLIANT`）。

  **红线 3（采集迹象）**：`params` 中出现**任意**信号字段却未能识别出数据类型 ⇒
  「处理行为存在 + 类型未知」⇒ 一律 `needs_review=true`（`unresolved_dtype_but_signal_present`），
  绝不判 `COMPLIANT`。实测该判据修复了 26.86% 的漏判（未收录 SDK 场景）。

## 1. 输入整体结构

判定服务的输入是**单条文本**，由 Hook 层按以下固定三段拼接：

```
[platform={android|ios|miniprogram|harmony}]
stack: {栈帧链，帧间用 ' <- ' 分隔}
params: {JSON 对象}
```

- `platform` 标记缺失时服务会按栈帧特征推断，但**强烈建议始终携带**（推断失败将判 UNKNOWN 入复核）。
- `params` 必须是合法 JSON（UTF-8，无注释）。解析失败时该样本降级为"参数不可解析"入复核队列。

## 2. 信号字段（判定依据，键名固定，不可改名）

| 字段 | 类型 | 取值 | 缺失时语义（fail-closed 策略） |
|---|---|---|---|
| `consent_state` | string | `granted` / `denied` / `not_requested` / `revoked` | 查 `consent_log`；两者皆缺 → **视为未取得同意（NO_CONSENT）** |
| `consent_scope` | string[] | 同意覆盖的数据类型列表 | 缺失时 `granted` 无法确认范围 → 按 NO_CONSENT |
| `consent_version_expired` | bool | 同意版本是否过期 | 缺失按 false |
| `consent_log` | string | `granted:TYPE,TYPE`（替代证据）/ `absent` / `revoked@...` | 仅作 consent_state 缺失时的替代证据 |
| `policy_disclosed` | bool | 隐私政策是否已告知 | 缺失按 true（不因缺字段误判未告知） |
| `policy_updated_after_consent` | bool | 收集后是否修改政策且未重新告知 | 缺失按 false |
| `crypto` | string | `AES-256-GCM` / `TLS1.3` / `SM4-GCM` / `RSA-OAEP` / `ChaCha20-Poly1305`（合规）；`none` / `raw` / `DES-ECB` / `AES-ECB`（不合规） | 缺失时查 `transport`；两者皆缺 → 中置信入复核 |
| `transport` | string | `https` / `http` | `http` 直接判明文传输 |
| `pii_mask` | string | `masked` / `partial` / `raw` | 缺失 → 中置信入复核 |
| `biz_purpose` | string | 见 §3 业务必要性映射 | 缺失不做过度收集判定 |
| `collect_scope` | string | `minimal` / `all` | 缺失按 minimal |
| `extra_fields_collected` | bool | 是否搭车采集额外字段 | 缺失按 false |
| `retention_days` | int | 留存天数，>365 触发 WARNING | 缺失不触发 |
| `data_destination` | string | `self` / `third_party` | 缺失按 self |
| `separate_consent` | bool | 向第三方提供时是否取得**单独同意**（PIPL 第23/29条） | 缺失按 true |

**红线**：任何字段改名 / 复数化 / 大小写变更都等于"字段缺失"，将触发 fail-closed 或复核，
Hook 层不得单方面变更。新增噪声字段（任意键名）不会影响判定，欢迎携带。

## 4. 数据类型识别（服务侧，由栈帧 + 参数键名 + consent_scope 完成）

服务按平台匹配真实 SDK API token（`apis.py` 目录）识别数据类型：
- android: `LocationManager.getLastKnownLocation`、`TelephonyManager.getImei` 等
- ios: `CLLocationManager startUpdatingLocation`、`CNContactStore contacts`、`LAContext evaluatePolicy` 等
- miniprogram: `wx.getLocation`、`wx.getUserProfile`、`wx.chooseContact` 等
- harmony: `geoLocationManager.getLastLocation`、`sim.getSimTelephoneNumber`、`contact.queryContacts` 等

**五级降级识别**（详见 §0 表格）：完整 token → 类名 token → 方法名 token →
payload 键名（`phone`/`idcard`/`contacts`…）→ `consent_scope` 类型名。

**四级与五级仍失败时必须 fail-closed**（v1.1 原文"仍失败 → `NONE`"**已废弃，是错误规则**）：
- 无混淆痕迹 + 无敏感语义词 + `params` 无任何信号字段 → 才判 `NONE||COMPLIANT`
- 否则（有混淆痕迹 / 有敏感语义词 / 有信号字段）→ `needs_review=true`，绝不判合规

## 5. 判定优先级（多个违规并存时输出最高优先级）

```
NO_CONSENT > NOT_DISCLOSED > PLAINTEXT_TRANSMIT > NO_MASK > OVER_COLLECT > WARNING > COMPLIANT
```

## 6. 服务输出契约（predict.py）

```json
{
  "data_type": "LOCATION",          // 14 类之一；解析失败为 null
  "violation": "NO_CONSENT",        // 7 类之一；解析失败为 null
  "combo": "LOCATION||NO_CONSENT",  // 92 组合之一
  "confidence": 0.99,               // 校准后置信度
  "source": "rules",                // rules | model(mmBERT-finetuned) | model(tfidf-fallback)
  "needs_review": false,            // true 时必须进入人工复核队列
  "review_reason": null,            // 如 "no_consent_evidence;rules_model_conflict(...)"
  "backend": "mmBERT-finetuned"
}
```

**生产 SLA 约定**：`needs_review=true` 的记录**不得**自动用于拦截/放行决策，必须人工复核；
复核结果回流入训练数据（含真实标签）用于持续微调。

## 7. 已知局限（诚实声明）

- 所有当前指标基于**合成分布**。上线前必须用真实脱敏日志复测（`--in real.jsonl`）。
- 规则引擎 100% 一致是"策略实现自证"，不构成模型能力证据；模型独立精度见
  `reports/finetune_metrics.json`（含 macro-F1 / per-class）。
- 弱加密枚举（DES-ECB/AES-ECB）之外的新算法名会被视为未知值——policy 对未知 crypto
  按"非明文"处理，Hook 层发现新算法时须同步更新 BAD_CRYPTO 白名单。

## 8. 保证与校准（★ v1.3 新增 —— 把"99.9%"变成可证明命题）

"漏判率 ≤ 0.1%"是一个**可证伪的统计命题**，不是一个功能开关。它的成立条件写在这里，
因为**其中最关键的变量由本契约决定**：

```
漏判率（条件口径）= 自动判 COMPLIANT 且真值非 COMPLIANT 的数 / 真值非 COMPLIANT 总数
```

**A. 唯一的数学障碍是基础风险 μ，而 μ 由输入是否守约决定。**
实测（`calibrate.py`，各 2500 条，α=0.001）：

| 输入情形 | μ | 弃判率下界 (μ−α)/(1−α) | 结论 |
|---|---|---|---|
| 契约合规（§0/§2 齐全） | **0.0000** | 0 | 0.1% 可达，人工率仅 0.88% |
| 栈帧 API 名未知（S1/S2） | **0.0000** | 0 | 0.1% 可达，人工率升至 73.8% |
| **契约违约**（信号字段被改名，S3） | **0.2602** | **0.2595** | 0.1% 仍可达，但**数学上强制** ≥26% 人工率 |

> 该下界来自 arXiv:2606.29054：μ > α 时任何 distribution-free 方法都必须弃判 ≥(μ−α)/(1−α)。
> 它**不能**靠更聪明的算法消除，只能靠"让输入守约"消除。

**B. 因此契约 §0.1（`consent_scope`）不是可选优化，而是 99.9% 的前置条件。**
实测：把"未见 API + payload 键名中性化 + 信号字段全缺"这一违约输入喂进来，
违约时漏判 **71.9%**；开启 `PC_SCOPE_CONTRACT=1`（契约 v1.2）或 `PC_STRICT_NONE=1` 后
漏判 **0.0000%**（全部 fail-closed 转人工）。二者的差别只是"人工单数量"。

**C. 部署 λ 由 `models/calibration.json` 提供，缺省即 0.9（行为与历史逐位一致）。**
- 未获认证的校准集（`guarantee=false`）**只能收紧**（λ 被钳到 ≥0.9），不得放松 ——
  否则一份在合成分布上"零漏判"的校准集就能把系统放宽到自动放行低置信样本。
- 间接识别层（Tier2/3/4/5）有**契约地板** λ ≥ 0.86，与该文件无关、不可越。
- 生产放行请设 `PC_REQUIRE_CALIB=1`：缺认证校准集时 `check_runtime.py` 的 C10 会记 `!!`。

**D. 尚未满足的条件（不可对外声称 99.9%）。**
- 校准集必须是**人工标注的真实脱敏日志**；当前所有数字来自合成分布。
- 交换性不成立（版本/新 SDK/Hook 格式漂移），严格保证需按 **platform × SDK 厂商** 分组；
  实测本数据集有 41 组，需 **41 × 999 ≈ 40959** 个真违规校准样本，当前远未达到。

### 8.1 证书不可自证（★ v1.4：红队 P0-1 修复）

**缺陷**：`guarantee=true` 原先只凭校准文件里的一个布尔字段。而 `--alpha` 是用户旋钮，
有限样本下界又恰好用它计算（`n_min = ⌈1/α⌉−1`）。于是

```
python calibrate.py --real --alpha 1.5 --write   # ⇒ n_min=0
```

即可写出 `guarantee=true` 的 `models/calibration.json`，而 `calib_runtime` 又会
**据此把 λ 放松到 0.9 以下** ⇒ 净增漏判。同一根因还让报告打印出
「分组保证：已认证（每组需 ≥0 个违规样本）」这种**凭空认证**。

**修复（五重）**：
1. **α 只能在生产目标上签发**：`ALPHA_TARGET = 0.001`。传 `--real` 时 α 被强制回
   该值（**只能收紧**），且在 `argparse` 之后**立即**生效 —— 必须在任何计算之前，
   否则分组认证仍会用用户 α 算出 vacuous 的"已认证"。
2. **分母用真违规条数**：`n_violation ≥ ⌈1/α⌉−1`（条件口径的正确分母；用总行数是乐观的）。
   `--delta δ` 启用 PAC 口径时改用 `n ≥ ln(1/δ)/(2α²)`（≈1.5e6）—— 声明的强度
   必须与校验的强度匹配（原实现声明 `train_cond` 却只校验 999）。
3. **来源闸门**（独立复核发现）：数量够 ≠ 来源对。打包的合成集真违规数恰 > 999，
   纯数量闸门挡不住，故追加两道：① `--data` 内容哈希命中内置合成集 ⇒ 拒绝；
   ② 必须显式 `PC_ALLOW_REAL=1`（与 `PC_ALLOW_RELAX` 同源的显式 opt-in 纪律）。
4. **读取端独立复核**（`calib_runtime.guarantee_verdict()`）：**不信任文件自称**，
   重算 `α ≤ 0.001` 且 `n_violation ≥ ⌈1/α⌉−1`；任一不满足 ⇒ 视为未认证，λ 钳回 ≥0.9。
   **类型严格**：`guarantee` 必须严格是布尔 `True`（`"false"` 这类非空字符串在真值
   判断下会被当成 True —— 与 `policy.py` 已立规的坑同源）；`alpha` 必须是数字，
   不接受 `"0.001"` 字符串。
   **V1(a)（第二轮独立复核）**：原实现把"键存在但类型不对"**静默降级**为退回总行数 `n`，
   于是 `{"n_violation": true, "n": 1000000}` 白过有限样本墙 —— 因为总行数恒 ≥ 真违规数，
   是**乐观分母**，而条件口径的分母**只能是**真违规数。现已彻底去掉一切"退回 `n`"路径：
   分母**必须**是 `n_violation`（`int` 且非 `bool`，非负，`≤ n`（若 `n` 存在），
   `≥ ⌈1/α⌉−1`）。`isinstance(True, int)` 为真这一 Python 陷阱单独设防。
   **本次进一步收紧**：连"键缺失就退回 `n`"也删掉了 —— 本项目校准器**恒**写 `n_violation`
   （其 `guarantee_type` 只取 `marginal`/`train_cond`/`none`，**从不**是"仅联合口径"），
   且官方指标是**条件**漏判率，拿不出 `n_violation` 的证书本就无法支持所声称的保证。
   代价仅是"拒绝一个本就无法验证的外来证书"——正是 fail-closed 方向。

   **V3（第三轮独立复核）补上的三个洞**：
   1. **崩溃/DoS**：`alpha=5e-324`（最小次正规数）使 `1/α = inf` ⇒ `math.ceil(inf)` 抛
      `OverflowError`。而 `guarantee_verdict()` 在**每次 `classify()`** 都会被调用 ⇒
      **伪造一份 `models/calibration.json` 就能让整条引擎崩掉**。fail-closed 的本意是
      "拒绝"，绝不是"抛异常"。修复：共享助手 `n_min_required(alpha)` 把"α 不可计算"
      （下溢/上溢/NaN/inf）显式折返 **None**，调用方按"拒绝"处理
      （verdict=`alpha_not_computable`），`classify()` 全路径与 `calib_status()` 均不再抛。
   2. **`n` 类型不对 ⇒ `≤n` 一致性检查被静默跳过**：`{"n_violation":1e6,"n":5.0}`
      （5 行里 1e6 个违规，自相矛盾）原会**通过**。与 V1(a) 同根因：**"键存在但类型不对"
      绝不能等价于"键不存在"**。修复：`n` 存在即必须为合法 int（非 bool）、非负，
      否则拒绝（`n_wrong_type`）。
   3. **放行开关可见性**：`PC_AUTO_LAMBDA=0.55` + `PC_ALLOW_RELAX=1` 可让 λ 落到 0.9 以下
      而**无需任何证书**。这是有意保留的实验通道（统一 env 纪律：放松须显式 opt-in），
      但"安全网不可用必须响亮"同样适用于"放行开关正在生效"—— `check_runtime.py` **C10**
      现在会对 `PC_ALLOW_RELAX=1 且 PC_AUTO_LAMBDA 已设` 记 `!!`（生产出现即为异常配置），
      只设其一记 `??`。
5. 产物新增 `provenance`（`attested: self`、`is_bundled_synthetic`、`allow_real_env`、
   `guarantee_floor_used`）、`guarantee_type`、`alpha_eff`、`assumptions`。

> 诚实边界：`--real` 仍是**上游自证**（无外部签名）。来源闸门只挡"误把合成集当真实日志"
> 与"随手加 --real"，**不能**证明标签确实经人工标注。读取端只做**数值**复核。
> 故 `guarantee=true` 的最终可信度仍需人工审计背书。

### 8.2 空声明安全网（★ v1.4：抽样 + 撤销，与"内容"正交）

`consent_scope: []` 是**上游自称**。红队给出可达漏判：未收录 SDK + 空声明 + 真实手机号
曾被自动判 `NONE||COMPLIANT`。已加两道**静态**阻断（值级 PII 形态印证、声明矛盾），
但它们都依赖"猜得到攻击形态"。故再加两道**与内容正交**的机制：

#### 8.2.1 值级形态必须**独立成立**（独立复核 C2 → **V2**）

**这段被两轮独立复核打穿过，是本项目最典型的"自我评价过高"案例。**

首版值级规则是**整串 `^…$` 锚定**，于是下列**廉价规避**全部逃逸，当时**仅**被可关闭的
dtype 哨兵兜住 ⇒ `PC_DTYPE_GUARD=0` 即泄漏。第一轮（C2）补强为"三种归一化 + 内嵌子串扫描"
并宣称已封堵；**第二轮（V2）随即用 22 种真实等价写法推翻该普适断言**（0/22 拦住）：

| 规避族 | 代表样本 | C2 版 | V2 版（现） |
|---|---|---|---|
| 分隔符 | `138-0013-8000` / `138 0013 8000` / `(138)0013.8000` | ✗ | ✓ |
| 分隔符（未覆盖） | `138_0013_8000` `/` `\|` `·` `–` `—` `,` | ✗ | ✓ |
| 全角数字 | `１３８００１３８０００` | ✗ | ✓（NFKC） |
| **其他数字系统** | `١٣٨٠٠١٣٨٠٠٠`（阿拉伯-印度）、`०१२३…`（天城文） | ✗ | ✓（14 种同形字折叠） |
| **不可见字符** | `138\u200b0013\u200b8000`、`\ufeff138…` | ✗ | ✓（显式零宽表） |
| **字面转义** | `"\\u0031\\u0033…"`（JSON 二次编码后剩字面 `\u0031`） | ✗ | ✓（转义还原） |
| **前导零** | `013800138000`、`0013800138000` | ✗ | ✓（`(?:0086\|00\|86\|0)?0*`） |
| **科学计数法** | `1.3800138e10` | ✗ | ✓（展开为整数串） |
| **JSON 数字** | `{"event":13800138000}`（非字符串标量，原实现**看不见**） | ✗ | ✓（标量迭代含 int/float） |
| **JSON 浮点** | `{"event":13800138000.0}` | ✗ | ✓（归一小数尾） |
| **分片键** | `{"a":"138","b":"00138000"}` | ✗ | ✓（跨值拼接后扫） |
| 坐标分隔/后缀 | `31.23;121.47`、`31.23N,121.47E` | ✗ | ✓ |
| 坐标小数位 | `31.23,121.47`（原要求 ≥4 位） | ✓ | ✓ |

**根因（方法论层面）**：把"归一化"当成**可选项**而非**必需环节**，且只做**一层**。
现改为**三级管线**（`rules_engine`）：

1. **字符级等价** `_text_variants`：去字面转义 → NFKC → 去零宽 → 折数字同形字（组合，≤8 变体）；
2. **数字级规范化** `_digit_canon`：去**全部**分组/破折号/中点分隔符 → 展开科学计数法 → 归一小数尾零；
3. **结构级**：直接用 ① 的变体（**保留** `.` `,` —— 坐标不能被"去分隔符"破坏）。

再加三层**互补入口**：① 逐值锚定（含 base64/hex 解码复检）→ ② 跨值拼接（分片规避）→
③ 规范化参数体原文扫描（非法/截断 JSON，如 `"event":013800138000` 因前导零不是合法 JSON）。

**零回归的依据不变**：本检测**仅在 `consent_scope: []` 显式空声明时**启用，而干净语料
30000 条里显式空声明出现 **0** 次（实测）⇒ 任何"放宽/多报"都不会影响正常流量；即便误报，
代价只是"多转人工"（fail-closed 方向），不是漏判。

**降噪**：`opaque` 的 32 字符阈值会吞掉 UUID / MD5 / SHA 这类常见非 PII 标识，故按**规范形态**
豁免（`_OPAQUE_UUID_EXEMPT` / `_OPAQUE_HEX_EXEMPT`）；这不削弱攻击覆盖——手机号 hex 编码只
22 个 hex 字符、base64 只 16 字符，都落不进这两种形态。

`check_hardening.py` **H5** 在 `PC_DTYPE_GUARD=0`（关掉软层）下断言 **76 种**规避（C2 的 19 +
V2 的 23 + **V3 的 16** + **V4 的 18**）全部转复核，并额外断言 **软层开/关结论一致**、时间戳 / ISO 时间 /
短串 / MD5 / UUID **不**被误判。要点：**主规则必须独立成立，哨兵只能是纵深防御**，不能是承重墙。

#### 8.2.1.1 数字折叠**禁止枚举数字系统**（V3 复核的最贵一课）

第二版为了堵"阿拉伯-印度/天城文数字"，**手工枚举了 14 个 Unicode 数字区块**。第三轮独立复核
立刻用**第 15 种**（僧伽罗 `U+0DE6`）加缅甸/高棉/桑塔利/绍拉什特拉/瓦伊/巴厘，以及
**ASCII+异体混写**（`"1" + 僧伽罗 10 位`）再次推翻 —— 16 个新泄漏，其中 15 个只被软层兜住。

**根因**：对**无穷等价类**做枚举，永远只能覆盖"已经发生过的写法"。Unicode 里"同一个
十进制数"的写法有几十套脚本，且**会继续新增**（Unicode 每年都在加数字脚本）。

**正解**：用 Unicode 自身的 `Numeric_Type=Decimal` 属性折叠 ——
`unicodedata.decimal(ch)` 对**任何**十进制数字字符返回其整数值，与脚本/区块/版本无关：

```python
def _fold_digits(s):
    if s.isascii(): return s
    out = []
    for ch in s:
        try:    out.append("0123456789"[unicodedata.decimal(ch)])
        except (TypeError, ValueError): out.append(ch)   # 上标/罗马数字等非 Decimal
        # 注意 unicodedata.decimal 对 '²' 会抛 ValueError（它是 digit 不是 decimal）——
        # 恰好是我们想要的：只折叠"真正的十进制数字"，不引入误报
    return "".join(out)
```

**可迁移的规则**：凡"归一化"类逻辑，先问"这个等价类的**定义**是什么"，再用**平台提供的
规范机制**（Unicode 属性表、`urllib.parse`、`base64`）实现，**不要手抄清单**。

**V3 同时补上的其他洞**（全部由独立复核构造）：

| 洞 | 样本 | 修复 |
|---|---|---|
| **多层编码** | 双层 base64 `TVRNNE1EQXhNemd3TURBPQ==`（解一层仍是 base64）——原实现连软层开着都漏 | `_encoded_pii_hit()` BFS 逐层解码（≤3 层，层内去重） |
| URL 编码 | `%31%33%38…`、双层 `%2531…` | `_decode_variants` 加 `urllib.parse.unquote` |
| 度分秒坐标 | `31°13'48\"N,121°28'12\"E` | 坐标分量分两种形态（十进制度数/度分秒），**锚定与内嵌两处都要改** |
| 带度号坐标 | `31.23°,121.47°` | 同上（`°` 可选） |
| 非法 JSON 裸 token | `1_380_0138_000`（下划线分组 ⇒ 不是合法 JSON ⇒ 逐值层失明） | `_collapse_digit_seps()`：删数字间的分组分隔符（**刻意不含换行**，避免把两行 JSON 的相邻数字并成 11 位数） |
| 深嵌套 | 8 层 dict 里的异体数字（超出 `_iter_scalar_values` 的 depth=6 防爆栈上限） | 由**文本级扫描**兜底（对规范化后的参数体原文扫描，不受嵌套深度限制） |

> 工程注记：测试样本里值若含 `"`，必须写成 `\"` 才是合法 JSON —— 否则 `json.loads`
> 失败、逐值层整体失明，测出来的是"JSON 非法"而非"形态规则失效"。这类**测试脚手架 bug**
> 会让真实的修复被误判为泄漏（V3 复核时就混进了 2 条）。


#### 8.2.2 抽样 + 撤销（与内容正交）

| 机制 | 作用 | 上界 / 局限 |
|---|---|---|
| 确定性抽样审计 | 以服务端密钥 `PC_SCOPE_AUDIT_KEY` 对请求 HMAC，按 p 强制转人工；**上游不可预测、不可重投** | 逃逸路径漏判 ≤ (1−p)（期望口径）；**不能**降到 0 |

  `check_runtime.py` **C12** 记 `!!`（"只敢开契约、不敢配审计"必须响亮）。
- 抽样率与 λ 同源纪律：`PC_SCOPE_AUDIT_PERMILLE` **只能收紧**（≥50‰），

  避免评测/红队运行污染生产的撤销表。

### 8.3 判据去噪：子串伪歧义（★ v1.4）

Tier-1 token 匹配刻意用**子串**（让 `ImageCapture.takePicture` 能命中
`CameraXImageCapture.takePicture`）。代价：若 token S 是 token L 的**真子串**且两者都收录，
则文本含 L 时**必然**也匹配 S ⇒ 同一处 API 产生两个数据类型 ⇒ **伪歧义** ⇒ 白转人工。
全库实测**仅 2 对**碰撞：

| 短 token | 长 token | 短 dt | 长 dt | 影响 |
|---|---|---|---|---|
| `accountmanager.getaccounts` | `accountmanager.getaccountsbytype` | NAME | EMAIL | **异 dt ⇒ 真伪歧义** |
| `imagecapture.takepicture` | `cameraximagecapture.takepicture` | EXACT_IMAGE | EXACT_IMAGE | 同 dt ⇒ 无影响 |

**规则**：命中集里若某变体是**另一命中变体**的真子串，则丢弃它 —— 它的出现完全被更长的
那次命中解释，**信息量为 0**。被丢弃的 hit 记入 `rules_engine.suppressed_substring_hits()`
（语料基线：NAME×555、EXACT_IMAGE×285，**零条 verdict 变化**；显著偏离即告警）。
真正会丢证据的唯一情形是"两个 API 各自成帧同时出现"，实测 30000 条中 **0** 次。

### 8.4 目标②：人工预算（★ v1.4，LTT 式双约束）

`--human-budget B`：在「人工率 ≤ B」下**最小化漏判**。因漏判随 λ 单调不增、人工率随 λ
单调不减，最优点 = 可行域内**最大 λ**。预算不可行时**恰好等价于**不可行性下界
（§8 A. 的 (μ−α)/(1−α)）—— 此时**不应继续调 λ**，而应降低 μ（补全 API 目录 / 强化输入契约）。
`--delta δ` 启用**训练条件（PAC）**口径，样本需求升至 ≈1.5e6（默认关闭 = 仅边际保证）。

#### 8.2.1.2 解码层的职责纪律（V4 复核的两个结构性教训）

1. **豁免只管判定，不管解码**。`_OPAQUE_HEX_EXEMPT`（"32/40/64 位 hex 通常是 MD5/SHA"）
   曾被用来**短路 hex 解码分支**——于是 `hex(b64(phone))`（恰 32 个 hex 字符）直接漏掉。
   豁免的本意是"`opaque` **判定**不把 MD5 当 PII token"，不是"MD5 形态的串不许解码"。
   → 纪律：**一个 helper 只做一件事**；豁免写在判定处，解码层永远尝试解码
   （解出乱码自然不命中，对真 MD5 零误伤）。
2. **弱信号形态不出现在变换产物上**。`opaque`（≥32 字符 alnum）是弱信号，只该用于
   **原始值**；解码/反转产物动辄 32+ 字符（UUID 反转后仍是 36 字符）⇒ 会把良性长 token
   误报成 PII。→ 解码层只接受**强形态**（手机/身份证/银行卡/邮箱/坐标）。

**V4 同时补上的洞**：base64 无填充/夹空白、base32、`0x` 前缀 hex、冒号分隔 hex、全角 `％`、
HTML 实体（`&#49;`/`&#x31;` —— 否则剥离后得到**错位数字**，既不命中也不报错，最隐蔽）、
反转、CJK 表意数字/苏州码/罗马数字（`unicodedata.numeric` 且值为 0..9 整数；
**刻意排除** `十`=10、`万`=10000、`½`=0.5 —— 多位数值与分数折叠会产生语义歧义）、
单分量坐标（以 `°` 为判别器：`31.23°` 算，`3.14` 不算）、乱序/穿插分片（三元全排列），
以及**空声明 + JSON 解析失败 ⇒ 一律 fail-closed**（`empty_scope_unparseable_params`）——
最后这条是结构性闸门，消灭了"非法 JSON + 编码裸 token"一整类攻击。

#### 8.2.1.3 结构怀疑闸门与单一事实来源（V5 复核：枚举-结构螺旋的机制级收口）

V5 对抗验证用 **4 个系统性缺口类 + 17 个新规避**推翻了"收敛"断言，修复策略从
"逐个枚举编码器"升级为**两条机制级纪律**：

**纪律一：结构怀疑闸门（fail-closed 兜底，不判断产物是否 PII）。**
空声明分支的防线排序：

```
撤销回路 → 值级印证(_value_pii_shapes) → 结构怀疑闸门(_scope_structurally_suspicious)
  → 确定性抽样审计
```

值级印证只覆盖**已知形态**；其余一切"解不出来但结构异常"的值交给怀疑闸门——
五条启发式任一命中即转人工（`empty_scope_structure_suspicious:<reason>`），
**只产生嫌疑、不产生撤销**：

| # | 启发式 | 阈值 | 封住的家族 |
|---|--------|------|-----------|
| ① | `decodable_value` | 任一解码器解出 ≥8 可打印字符 | base85/ascii85/uu/双重 HTML 实体等白名单外编码 |
| ①b | `cross_value_encoded_shard` | 有序对拼接后解出 ≥8 可打印（≤132 组合） | 跨值 b64/b32/b85 分片（单片解不出） |
| ② | `excessive_value_count` | 标量值 >12 | 超长值表走私 |
| ③ | `excessive_nesting` | 嵌套深度 >6（值迭代上限，不可验证 = 嫌疑） | 深嵌套 × 编码 |
| ④ | `short_digit_shards` | ≥3 个 ≤6 位纯数字值 | 4 路/12 路数字分片（全排列 r≤3 治不了） |
| ⑤ | `dense_token` | **去空白后** ≥12 连续可打印 ASCII | 未知编码兜底 + 被剥空格的残缺 uu 行 |

**纪律二：契约闸门以"解析后的 JSON"为单一事实来源。**
正则首个匹配 vs `json.loads` 最后一个键的双轨语义，曾让
`{"consent_scope":[],"consent_scope":["PHONE"]}` 被自动放行**且永不可撤销**。
修复：空声明分支改用**严格** `json.loads` + `object_pairs_hook` 重复键拒绝
（`empty_scope_duplicate_key`）+ 解析后的 `consent_scope` 必须确为 `[]`
（否则 `contract_scope_mismatch`）；不可解析 / 非对象各给显式 review_reason。
**凡契约判定，一律读解析结果，不再读正则。**

**螺旋教训（写给下一轮）**：每轮"覆盖 X 种"的断言都会被等价类之外的构造推翻。
终止条件不是"我宣布收敛"，而是（a）重复缺口类上升为机制级 fail-closed 兜底、
（b）独立对抗验证者找不到新缺口。V5 修复后 H5 覆盖 93 种规避（软层开/关一致、
零泄漏），双口径回归逐位一致（0.0024/0.0128、0.0133/0.0236）。

#### 8.2.1.4 键名盲区、边界字母分片与 DoS（V6 对抗复核：三个与 V5 正交的缺口）

V5 修复后立刻被第六轮对抗复核打回 **PARTIAL**——四项修复无一被正面攻破，但找到
**2 个正交泄漏族 + 1 个单核挂死级 DoS + 1 个崩溃窗口**：

1. **键名盲区（无条件泄漏）**。解码/形态/结构闸门只扫**值**；PII 进键名
   （键名 base64/hex/base32）或拆在键/值两侧（`{"138":"00138000"}`）、
   键/键两侧（`{"138":"x","00138000":"y"}`）⇒ 全层失明。
   → 修复：`_iter_keys` 递归收集全部 str 键名（排除声明字段 `consent_scope`
   本身，深度上限 8）并入检测池（值 12 + 键 12，去重 ≤24）；
   新增 **①c 有序对拼接形态扫描**（键+值 / 键+键拼出完整形态即嫌疑，
   廉价预筛：拼接串须含 ≥7 位数字 / `@` / `°`）。
2. **4 路分片 + 边界字母（关哨兵泄漏）**。`"a13"/"800"/"138"/"000b"`：r≤3
   全排列凑不出 4 路；两片不是纯数字，旧"纯数字 ≤6 位"计数漏网。
   → 修复：④ 计数升级为「**去非数字后长度 ∈ [2,8]** 或 **纯数字 ≤6 位**」
   （10+ 位时间戳不计入，误报面可控）。
3. **二次复杂度 DoS（D1）**。email 内嵌正则 `[\w.+-]+@[\w-]+\.[\w.]{2,}` 带无界
   量词：**不含 `@`** 的长文本上 search 逐起点回溯 ⇒ O(n²)——960KB 单值实测
   **>24 分钟**单核挂死，纯 CPU 可低成本放大。
   → 修复：`_shape_search` 对 email 做廉价预筛（无 `@` 必不命中 ⇒ 跳过；
   其余形态量词有界、线性，无需预筛）+ 闸门解码/拼接长度上限 16KB
   （超长值必然命中 ⑤ 密集 token 或 ③ 深嵌套，不损失检测）。
   修复后 960KB **0.44s**（`check_hardening.py` 有时序回归断言）。
4. **深嵌套崩溃窗口**。700~950 层嵌套 JSON 能解析（低于 Python 递归极限）但
   `_obj_depth` 无保护递归 ⇒ RecursionError 逃出 classify。
   → 修复：深度计到 8 即提前返回（闸门只判 >6，多算无收益）。
5. **指纹语义修正**：`scope_audit._KEYS_RE` 旧正则排除数字开头键名，与
   "键名集合"文档语义不符（方向是多撤销，保守）⇒ 放宽为任意非空键名。

V6 回归样本 10 条并入 H5 ⇒ 覆盖 **103 种**规避（软层开/关一致、零泄漏）；
双口径回归仍逐位一致；`calibrate.py --verify` mismatch=0。

#### 8.2.1.5 归一化缺失、截断窗口与复杂度封顶（V7 对抗复核：4 条泄漏链 + 2 条 DoS）

第七轮对抗复核判定 **CONFIRMED**（V6 被攻破）：干净分片全拦，但构造出 4 条
互相独立的泄漏链与 2 条秒级以上 DoS。修复把两条**机制级纪律**补齐：

**纪律三：拼接与密集性判定必须在归一化视图上进行。**
- **粘连字符打断**：`"6222021"+"2a34567890"` 一个 `a` 打断 `\d{16,19}` 连续段、
  2 片策略躲开"≥3 分片"计数。→ `_split_key_hit` 与闸门 ①c 的拼接串增加
  **`\D` 剥离候选**（≥11 位才扫）与 NFKC/零宽/折数字候选
  （`_concat_shape_candidates`）；全角/零宽键名分片现形。
- **非 ASCII 打破密集性**：每 ≤11 字符塞一个 `é`/零宽即可打破 `[!-~]{12,}`，
  V6"超长值由 ⑤ 兜底"的声明不成立。→ ⑤ 改为**剥掉一切非 `!-~` 字符**
  （`[^\x21-\x7e]`）后计数——内嵌编码 token 直接现形。

**纪律四：复杂度必须显式封顶，输入长度进入威胁模型。**
- **email 正则"有 @ 但匹配失败"仍是 O(n²)**（`"a"*100000+"@"` 实测 90s）——
  V6 的"无 @ 才跳过"预筛只治一半。→ 根治：**@ 定位 + ±80 字符窗口**匹配
  （RFC 5321 本地部分 ≤64，窗口足够）；@ 数 >256 直接判命中（fail-closed）。
- **全排列 × O(n²)**：12×2KB 值的组合扫描实测 81.8s（外推 8KB ≈ 21min）。→
  `_split_key_hit` 组合**长度帽 128**（内嵌形态 ≤40 字符；长值藏完整 PII 由
  单值内嵌扫描覆盖）；闸门 ①b 拼接解码帽 4KB、①c 形态扫描帽 128、
  单元素解码帽 16KB。修复后 D1b=0.16s、D2=0.41s（均有回归断言）。
- **截断窗口**：`keys[:12]` 让第 13 个键名藏编码 PII（`null` 值不计 ②）。
  → 键帽 32、池帽 48——组合数上升由长度帽保证不放大耗时。

**已知局限（明示，不在规则层解决）**：dtype 哨兵（L3 ML 层）对垃圾填充文本
返回 None、对正常短调用偶发误报——按"主规则必须独立成立"原则，哨兵只是
纵深防御，规则层零泄漏后其失效不构成泄漏路径；哨兵自身的再训练单列。

V7 回归样本 7 条 + 3 条 DoS 时序断言并入 H5 ⇒ 覆盖 **110 种**规避
（软层开/关一致、零泄漏）；双口径回归逐位一致；mismatch=0。

#### 8.2.1.6 窗口切割、截断窗口与 ASCII-only 兜底（V8 对抗复核：4 泄漏族 + 1 DoS）

第八轮对抗复核判定 **REFUTED**（规则层）：V7 修复在规则层独立成立下被 4 个
泄漏族攻破，统一根因是——**非 ASCII 字符（或键帽溢出）让所有 ASCII-only 兜底层
（⑤ dense 的 `[^\x21-\x7e]`、opaque 的 ASCII 锚定、①c 的 `isdigit()`）失明，
而主检测器被长度帽/窗口截断**。修复引入两条纪律：

**纪律五：窗口/截断是失明，不是封顶。**
- **email ±80 定长窗口**被 100 个 é 的域名标签撑破（`.com` 截出窗口）⇒
  email 失明、⑤ 剥非 ASCII 后域名归零。→ `_email_embedded_hit` 改**结构化扫描**
  （@ 两侧沿 `\w` 走完：本地 ≤64、域名 ≤512，超长未闭合 fail-closed，无窗口切割）。
- **键帽 32 截断**让第 33 键藏编码 PII。→ 键数 >32 直接 `excessive_key_count`
  （超限即 fail-closed，不再截断）。
- **128 拼接帽**把 `"é"*118+"138"` 的 129 字符 concat 跳过。→ `\D` 剥离候选
  **不受原始长度帽限制**（数字分片本就短；帽只约束正则输入）。

**纪律六：归一化/折叠必须与预筛一致。**
- ①c 预筛 `ch.isdigit()` 只认 Decimal 型数字，漏 Numeric 型（一/〇/〡/①），与
  `_fold_digits` 的折叠能力不一致 ⇒ 表意/苏州码/圈数字键值分片漏判。
  → 去预筛；`_is_shard` 也改为先 `_fold_digits` 再计数。
- 长拼接的 NFKC+折数字有 512 字符护栏（C 级 `\D` 剥离兜底），修 DoS 又保覆盖。

**DoS 收口**：`_fold_digits` 加 `isnumeric()` 预筛（非数字非 ASCII 字符从 2 次
unicodedata 查表降到 1 次 C 调用）；`_uudecode_line` 加 4096 长度护栏（uu 是行
编码，行长有限）。1.5MB 纯中文值 8.8s → 2.79s（线性高常数，非 O(n²) 爆增）。

V8 回归样本 6 条 + 1 条 DoS 时序断言并入 H5 ⇒ 覆盖 **116 种**规避
（软层开/关一致、零泄漏）；双口径回归逐位一致；mismatch=0。

#### 8.2.1.7 修复引入的回归也是攻击面：V8 修复 C 触发的 77s DoS 与 quoted-string email（V9 对抗复核）

第九轮对抗复核判定 **PARTIAL**（规则层）：V8 的四项修复无一被正面攻破，
但验证者构造出 **1 个严重 DoS 回归 + 1 个低严重度 email 漏判**，且**前者正是
V8 修复 C 自身引入的**。这是新的方法论信号：**每一次修复都要重新进入威胁模型，
修 A 可能替 B 开洞。**

**泄漏 1（低严重度）— email quoted-string 本地部分漏判。**
RFC 5321 允许 quoted-string 本地（`"john doe"@example.com`）。旧 `_EMAIL_LOCAL_CH`
字符集为 `[\w.+\-]`，扫描遇到 `"` 即判"无本地"并跳过 ⇒ `"a"@b.com` 无条件泄漏。
→ 字符集补 `"`，扫描不因引号提前终止（引号是 quoted-string 的**合法起止符**，
不是"无本地"信号）。

**DoS 回归（严重）— V8 修复 C 的副作用。**
V8 修复 C 为让 `\D` 剥离候选"不受原始长度帽限制"，把正则剥离移到了长度帽之外；
但剥离对象是**逐对全排列拼接后的原始长串**，12×200KB 中文全排列时 `re.sub` 累计
处理 ≈1.0e8 字符（cProfile 定位 cumtime 62.9s 全在 `_fold_digits`），实测 **77s**。
这是"为覆盖而放松复杂度约束"的直接反噬。→ 三重收口：
1. **逐值预提取数字候选** `_digit_extract`：每个值只做一次 NFKC+折数字+`\D+` 剥离，
   全排列只对**数字串**（长度 O(总数字数)，一次性）做组合，而非对每对原始长串做
   正则；
2. **64KB 折叠帽 `_FOLD_CAP`**：单值超 64KB 直接跳过 `_fold_digits`/NFKC 逐字符
   处理（长值由 ③ 文本级 C 正则或 ⑤ dense token 兜底，嵌入 PII 仍被捕获）；
3. **`\D+` 而非 `\D`**：一次匹配整段非数字，避免逐字符回调。

**两条新纪律**：
- **纪律七：修复即攻击面。** 每次修复都必须重跑复杂度威胁模型——"把某个操作移出
  长度帽"这类看似局部的改动，会把 O(n) 放大成 O(n²)（全排列 × 长串）。
- **纪律八：复杂度封顶要用"预计算 + 有界形式"，不是"排除输入"。** 正确的封顶是
  把昂贵的归一化/剥离**移到循环外、逐值做一次**，让组合阶段只碰短的数字串；
  而非简单跳过超长输入（那会重新制造失明窗口）。

**V9 修复后状态**：12×200KB 中文全排列 77s → 2.03s（线性）；quoted-string email
已拦截。H5 覆盖 **118 种**规避（C2:19 V2:23 V3:16 V4:18 V5:17 V6:10 V7:7 V8:6
V9:2）+ **5 条 DoS 时序断言**，软层开/关一致、零泄漏；双口径回归逐位一致；
mismatch=0。

#### 8.2.1.8 修复的"帽"反成攻击面：V9 的 `_FOLD_CAP` 盲区与短 base64 分片（V10 对抗复核）

第十轮对抗复核判定 **REFUTED**（规则层）：V9 的修复无一被正面攻破，但验证者
构造出 **2 个漏判 + 1 个 DoS**，其中两个直接打在本轮刚做的修复上——这是"修复即
攻击面"纪律（§8.2.1.7 纪律七）的再次兑现，且暴露了一条更尖锐的教训：**为省
复杂度而加的"跳过/帽"，本身可能引入一个比它更隐蔽的等价类盲区。**

| 缺口 | 根因 | 修复 |
|------|------|------|
| ① 短编码多片跨值分片 | ①b 只做"拼接后解码"；`MTM4`/`GEZTQ`/`313338`（<8 字符）被 `_decode_variants` 的 `len<8` 护栏跳过 | `_short_decode`（base64≥4/base32≥2/hex≥2 且偶数）+ ①d "解码后分片重组"（r≤3 数字全排列 + ≥3 短数字片计数兜底 4+ 片） |
| ② 帽外表意数字 | V9 的 `_FOLD_CAP=64KB` 让超长值跳过折叠，`\D+` 剥离**销毁**表意/苏州码/〇（非 `\d`） | 取消折叠帽：`_digit_extract`/`_fold_digits` 统一折叠（逐元素只调一次，O(n) 单次可接受） |
| ③ 重复键 O(n²) DoS | `keys.count(k)` 每键 O(n) 扫描 ⇒ 3 万键 31s | `Counter` 一次计数 O(n) |

**三条新纪律**：
- **纪律九：为省复杂度而加的"帽/跳过"必须先问"帽外谁兜底"**——V9 的 64KB 折叠帽
  假设"NFKC 会折叠全角/圈数字、`\D+` 会保留 ASCII 数字"，但**表意/苏州码/〇 既不
  被 NFKC 折叠、又被 `\D` 当非数字销毁**，两端假设同时落空 ⇒ 帽外失明。正解不是
  更细的帽，而是**取消帽、改逐元素单次折叠**（复杂度封顶靠"移出循环"，不是"排除输入"）。
- **纪律十：编码分片有两个正交方向**——"拼接后解码"（①b）与"各自解码后拼接"（①d）。
  前者被填充居中/`len<8` 护栏击破，后者是独立等价类。两条都要有，且**短片段（base64 4
  字符 / base32 2 字符 / hex 2 字符）也要能解码**；**任意多片（4+）由"解码后短数字片 ≥3"
  计数兜底**，不再靠 r 上限枚举（fail-closed 方向，短解码只增转人工）。
- **纪律十一：确定性引擎的"确定性 O(n²)"是静默 DoS**——`list.count` 在解析钩子里的
  二次方扫描，3 万键即可挂死单核 31s。任何 `x in list` / `list.count` 在**循环里**都要
  换成哈希（`set`/`Counter`）。

**V10 修复后状态**：重复键 31s → 0.31s；帽外表意数字、短编码 3~5 片均转复核。H5 覆盖
**122 种**规避（…V9:2 V10:4）+ **6 条 DoS 时序断言**，软层开/关一致、零泄漏；
双口径回归逐位一致；mismatch=0。

#### 8.2.1.9 反转分片、uu/ascii85 的"空格语义"与值数无上限 DoS（V11 对抗复核）

第十一轮对抗复核判定 **REFUTED**（规则层）：验证者构造 **3 个漏判 + 1 个 DoS**，
继续兑现"修复即攻击面"与"任一帽必须回答帽外谁兜底"两条既定纪律。本轮的三条
根因里，有两条都落在**编码/反转的边界字符语义**上——即"解码函数接收到的输入
是否保留了它本来的字节"：

| 缺口 | 根因 | 修复 |
|------|------|------|
| ① 反转分片（值/键名） | `_digit_extract` 只取原串数字，`"1" + reverse("0008310083")` 拼出 `13800138000` 但原串数字 `10008310083` 不命中 | `_digit_cands`：每值贡献**原串 + 反转串**两路数字候选（去重） |
| ② uu 短行分片 | uuencode 用空格（值 0）编码尾部零字节，`pool=[s.strip()]` 把尾空格销毁 ⇒ `n > len(data)` 解码失败；且每片 <12 字符 ⑤ 兜不住 | `_decode_variants` 的 uu 分支用**原始 s**、只 `rstrip("\r\n")`（保留尾空格） |
| ③ ascii85-adobe `<~ ~>` 分片 | `base64.a85decode(t)` 默认 `adobe=False` 不剥定界符 ⇒ 带定界符整片解不出 | `base64.a85decode(t, adobe=True)`（标准 Adobe ascii85 定界符） |
| ④ 值数无上限 DoS | `_value_pii_shapes` 在结构闸门**之前**对全部值逐值扫描，50 万值 ~35s | 逐值只扫 `values[:12]`，与结构闸门 `>12 → excessive_value_count` 同阈值兜底 |

**三条新纪律**：
- **纪律十二：反转是独立等价类，且必须与"原串数字"并列成候选**——分片重组只看
  原串数字，会让 `"1" + reverse(...)` 这类把前缀拆到反转侧的攻击整体漏判。数字
  候选 = `_digit_cands(原串) ∪ _digit_cands(反转串)`，每值多 1 个候选即可封死。
- **纪律十三：解码函数的输入必须保留原始字节语义**——uuencode 的尾空格是**数据**
  （零字节填充），不是可剥的空白；ascii85 的 `<~ ~>` 是**定界符**，不是待剥离的
  装饰。任何对解码输入的 `strip()`/`lstrip()`/`rstrip()` 都要先确认它不是编码本身
  的组成部分；做不到"无损"的预处理，就等于在解码前先销毁了信息。
- **纪律十四：结构闸门是复杂度护栏，必须"先判闸、再逐值"**——`_value_pii_shapes`
  对全部值逐值扫描，与 `_scope_structurally_suspicious` 的 `>12` 闸门**顺序颠倒**
  （逐值扫描先跑），50 万值即挂死单核 35s。任何"逐元素扫描"都要先问：是否有结构
  闸门能提前 fail-closed？有就**同阈值截断**（`values[:12]`），让两者永远一致。

**V11 修复后状态**：反转分片、uu 2/3 片、ascii85-adobe 4 片均转复核；10 万值值数
DoS 1.18s。H5 覆盖 **124 种**规避（…V9:2 V10:4 V11:2）+ **9 条 DoS 时序断言**（含
V11 值数 DoS），软层开/关一致、零泄漏；双口径回归逐位一致；mismatch=0。

#### 8.2.1.10 整数进制编码：一个信息论上不可枚举的等价类（V12 对抗复核）

第十二轮对抗复核判定 **REFUTED**（规则层）：验证者发现 **base36 / base62 / base58**
等"整数进制编码"——把手机号**整数** `13800138000` 用 `int("6c88umo", 36)` 压成 6–11
字符的紧凑 alnum token。它绕过所有既有防线：① 不在字节解码白名单（base64/32/hex/…）
内；② 短于 ⑤ dense_token 的 12 阈值；③ `_digit_extract` 剥非数字后只剩 `"688"`，凑不回
11 位。**这不是又一个可枚举的编码器，而是一个信息论上不可枚举的等价类**：

| 缺口 | 根因 | 修复 |
|------|------|------|
| 整数进制编码（base36/62/58/9/11/16/85/91/94…） | PII 整数被任意进制 N 重编码成 6–11 字符 token，形状被彻底抹除 | ⑥ 整数进制兜底：剥非可打印 ASCII 后 **6–11 字符且非纯数字**、或**恰 11 位纯数字** ⇒ 转人工 |

**为什么不能"解码后匹配形态"**（本轮最深教训）：手机号/身份证/银行卡**形态过宽**。
任意 9–11 字符 base62 token 解出的整数都落在 `\d{16,19}`（银行卡）区间内 ⇒
"解码→匹配银行卡"会对**几乎全部** 9–11 字符 token 全称阳性，等于没检测。而手机号
`1[3-9]\d{9}` 虽是窄带，但 6 字符 base62 token 落在该带内的比例仍高达 ~12%（
`[1.3e10, 2e10)/62^6`）。**一旦允许"整数→十进制"这个解码器，任意 token 都映射到
某个整数**，形状匹配退化为掷硬币。故唯一可做的判定是**token 的形状本身**：
- **6–11 字符非纯数字 token**：覆盖 base11–94（含字母/标点）。纯数字 ≤10 位是时间戳
  /小整数/ID（且 base≤10 的整数编码只会更长、被 ⑤/数字形态覆盖），故豁免。
- **恰 11 位纯数字**：覆盖 base9（首数字 3–5，不再匹配 `1[3-9]` 手机号前缀）与境外号。
- **拆片补丁**：base-N token 可拆到多个**值**（每片 <6 字符逃过单 token 阈值）——
  `{"a":"F3v","b":"yIy"}` 拼回 `F3vyIy`。⑥ 增加"≥2 个含字母值合计 ≥6 字符 ⇒ 转人工"。

**两条新纪律**：
- **纪律十五：解码后匹配形态只在形态足够窄时有效**——一旦某个解码器把"任意 token →
  某个整数"，且目标形态是宽区间（16–19 位银行卡），匹配就退化为随机。面对信息论上
  不可枚举的等价类，正解是按**变换产物形状** fail-closed，而非枚举解码器。
- **纪律十六：拆片是编码攻击的标配后缀**——任何"紧凑 token"都能再拆成短片规避单
  token 阈值；检测必须同时覆盖"整 token"与"多片重组"两个正交方向（与 §8.2.1.8 纪律十
  对字节编码的同源结论）。

**已知残余（信息论下限，诚实声明）**：① 把 base-N token 拆到**键名**
（`{"F3v":"1","yIy":"2"}`）——键名与描述性字段名不可区分；② 拆出**孤立纯数字片**
（`6c88umo`→`6c`+`88`+`umo`）——`88` 与良性小整数不可区分。二者都需要刻意切分且与
良性内容信息论同构，接受为残余，不进"已封堵"断言。

**V12 修复后状态**：base9–94 全进制手机号编码均转复核；base-N 拆片（值）转复核；
10 位时间戳/短词/小整数不受 ⑥ 影响（零误报）。H5 覆盖 **132 种**规避（…V11:2 V12:8）
+ **9 条 DoS 时序断言**，软层开/关一致、零泄漏；双口径回归逐位一致；mismatch=0。

- **纪律十七：ASCII 剥离 = 失明，不是归一化**——任何"剥掉非 ASCII 再看"的兜底，对

#### 8.2.1.12 拆片阈值可稀释、单字符键与小字母表非 ASCII 长 token（V14 对抗复核）

第十四轮对抗复核判定 **REFUTED**（规则层）：验证者证明 V13 声明的"信息论残余边界"
**不成立**——`sum(len)>=6` 阈值可被短占位值稀释、单字符键根本不在检查区间、16 字符
非 ASCII 帽被"更小字母表⇒更长 token"绕过。共 5 类新漏判 + 1 个线性 DoS：

| 缺口 | 根因 | 修复 |
|------|------|------|
| base36 键+值拆片（`{"umo":"6c88"}`） | ⑥ 只把"含字母值+含数字/混写片段键"计入且要求 `sum(len)>=6`；单含字母值 + 纯小写键 ⇒ 计数 1 不触发 | ⑥ 重写：ASCII 2–12 字符"字母+数字混写 或 大小写混写"片段（键或值）直接 fail-closed，不再依赖可稀释的 sum 阈值 |
| 3 路键拆片 + 短占位值（`{"6c":"x","88":"y","umo":"z"}`） | 值 x/y/z 各 1 字符 + 片段键 `6c` 总长 5 < 6 ⇒ 阈值被压穿 | 同上（字母+数字片段键单点即判，不再计数聚合） |
| 单字符键（`{"K":"pwjrm"}`） | ⑥ 片段键检查区间 `2..5`，长度 1 的键进不了区间；单字符键不可能是描述性字段名 | ⑥ 增"单字符字母/数字键 ⇒ integer_base_token" |
| base26/52/62 拆片系统性家族 | 换字母表后键+键/3 路/身份证/银行卡全漏——是"任意进制×任意拆法"的系统性失守 | 字母+数字（base36/62）与大小写混写（base52）片段已由 ⑥ 判定覆盖；base26 纯单大小写字母拆片见下方残余 |
| 小字母表非 ASCII 长 token（base2/3/4/…/11，17–34 字符 CJK token） | V13 非 ASCII 兜底设 16 字符**上帽**，心智模型"大字母表⇒短 token"遗漏反向 | ⑥ 非 ASCII 兜底改"len≥2 且可打印，**不设上帽**" |
| 20M/50M 非 ASCII 输入线性 DoS（19s/49s） | `_text_variants` 对整 params 体做 NFKC + 多次 re.sub/translate 的 O(n) 扫描，无长度硬帽 | `classify()` 顶部 `_MAX_TEXT_CHARS=8M` 直接拒绝（`input_oversized`）；空声明分支 `_MAX_BODY_CHARS=4M`（`empty_scope_oversized_body`） |

**两条新纪律**：
- **纪律十九：阈值/区间是攻击面，不是防线**——任何"sum≥N""len∈[a,b]"的可枚举判定都可
  被短占位值、路数、进制选择稀释或绕出区间。fail-closed 判定应基于**单点形状**（一个
  片段即判），而非多元素**聚合阈值**。
- **纪律二十："上帽"必须问反方向**——编码 token 长度随字母表**单调递减**，故"更小
  字母表⇒更长 token"；只设上帽（16 字符）会漏掉小字母表长 token。非 ASCII 兜底要么
  不设上帽（fail-closed 按形状），要么把长度上限与 PII 量级一起建模。

**已知残余（信息论下限，诚实声明）**：base26 **纯单大小写字母**片段拆片
（`{"bsr":"mvlim"}` = base26 的 13800138000，键 3 + 值 5 均纯小写）——与描述性词
`event/ts/ok` 信息论同构，无法在不误伤良性值的前提下区分，接受为下限。base36/62
（必含数字）、base52（大小写混写）片段已由 ⑥ 判定覆盖。

**V14 修复后状态**：除 base26 纯单大小写字母拆片（发现 4）外的全部 V14 样本均转复核；

双口径逐位一致（0.0024/0.0128、契约 0.0133/0.0236）；mismatch=0。

#### 8.2.1.13 符号字母表编码：⑥ 的字符类盲区（V15 对抗复核）

第十五轮对抗复核判定 **REFUTED**（规则层）：验证者证明"整数进制编码"的字母表不只是
`{0-9}∪{a-z}∪{A-Z}`，ASCII 里还有 **33 个符号字符**（`!"#$%&'()*+,-./:;<=>?@[\]^_`{|}~`）
可作字母表。⑥ 的判定只用 `isdigit/isalpha/isupper·islower` 四种谓词，符号字符落入三条
拦截的交空。共 3 类新漏判家族：

| 缺口 | 根因 | 修复 |
|------|------|------|
| 纯符号字母表（base33，`{"aa":"-`)_","bb":"^);"}`） | 符号片段 `_isd/_isa/_mixcase` 三者皆 False | ⑥ 增 `_hassym`：含"强符号"（除下划线外的 ASCII 标点）片段 fail-closed |
| 字母+符号（base59，`vb"`/`sn?`） | `_isd and _isa` 要求字母**和**数字同时，纯小写+符号无数字 ⇒ False | 同上（`_hassym` 单点即判，不依赖字母/数字组合） |
| 数字+符号（base43，`2,/{`） | 数字在 base43 里稀疏（10/43）被符号打散，`_digit_extract` 拼接重组 `len(nd)>=11` 失效 | 同上（`_hassym` 拦截符号片段，不依赖数字拼接路径） |

数组/嵌套对象（发现 4）只是换壳——`_iter_scalar_values`/`_iter_keys` 递归展开后片段字符
类不变，同被 `_hassym` 拦截。

**纪律二十一：字符类必须覆盖全集，谓词的交空就是失明**——"token 形状 fail-closed"若只用
字母/数字/大小写的布尔组合，会系统性漏掉**符号**这一整维。枚举字母表时必须以
`可打印字符全集` 为准（字母、数字、符号、非 ASCII），任何一类都要有对应的形状判定，
否则该类字符参与的编码就是可枚举、可复现的漏判。

**已知残余（信息论下限，诚实声明，不变）**：base26 **纯单大小写字母**片段拆片
（`{"bsr":"mvlim"}`）——与描述性词 `event/ts/ok` 信息论同构，接受为下限。base36/62
（含数字）、base52（大小写混写）、base33/43/59（含符号）、base>94（非 ASCII）均已覆盖。
至此"紧凑 token 形状"的判定已覆盖**除纯单大小写字母外的全部可打印字符类**。

**V15 修复后状态**：第 15 轮全部 11 个符号字母表/数组/嵌套样本转复核；良性 `event=ok/
ts/42` 与蛇形短标识符 `a_b` 零误报（`_hassym` 排除下划线）；软层开/关一致。H5 覆盖
**158 种**规避（…V14:9 V15:11）+ **11 条 DoS 时序断言**；5 个检查脚本 rc=0；measure_path
双口径逐位一致（0.0024/0.0128、契约 0.0133/0.0236）；mismatch=0。

#### 8.2.1.14 下划线字符类盲区：base27/28/11（V16 对抗复核）

第十六轮对抗复核判定 **REFUTED**（规则层）：V15 的 `_hassym` 为"防误伤蛇形标识符"而
刻意排除下划线 `_`，但这条排除的**两条理由都被实测证伪**，重新打开三族编码漏判：

#### 8.2.1.15 检测投影错位：可打印 ASCII 之外的整片编码空间（V17 对抗复核）

第十七轮对抗复核判定 **REFUTED**（规则层）：验证者证明 ⑥ 的判定建立在**有损投影**
`t = re.sub(r"[^\x21-\x7e]", "", v)` 上，并对 `t == ""` 的情况 `continue` 跳过——把
"投影为空"误当成"内容为空"。但 JSON 载荷**原样保留**空白/控制/非 ASCII 字符（剥离只
发生在检测侧），于是"内容完全落在可打印 ASCII 之外"的整片编码空间对 ⑥ 透明。两族新盲区：

| 缺口 | 根因 | 修复 |
|------|------|------|
| 空白/控制/Unicode 空白字母表（空格/制表/换行/回车/NBSP/em空格/全角空格，base2/4/3…，任意长度） | 这些字符全在 `[!-~]` 之外 ⇒ `t=""` ⇒ skip；⑤ 同一条 re.sub 也失明 | ⑥ 改"raw 非空但投影 `t` 为空 ⇒ fail-closed" |
| 非 ASCII 护栏边界：单字符非 ASCII（躲 `len>=2`）、可打印+不可打印混合（躲 `isprintable()`）、非 ASCII 键名 | 旧非 ASCII 兜底 `len>=2 and isprintable()` 只兜住很小一块 | 同上（投影为空即 fail-closed，覆盖 len==1、不可打印、键名侧） |

**纪律二十三：检测投影≠载荷内容**——"把非目标字符剥离后再看"是失明，不是归一化。
剥离只让检测看不见，载荷侧信息原封未动。任何"投影为空 ⇒ 跳过"的分支，都要先问：
**原始载荷是否真的为空？** 若原始非空而投影为空，说明内容整段落在投影之外，必须
fail-closed，而不是当成"无内容"放行。这一条把前几轮的"ASCII 剥离=失明"（纪律十七）
从"字符类内"推广到"投影内 vs 投影外"。

**已知残余（信息论下限，诚实声明，不变）**：base26 **纯单大小写字母**片段拆片
（`{"bsr":"mvlim"}`）——与描述性词 `event/ts/ok` 信息论同构。V17 发现 3 进一步论证：
熵/元音辅音/字典/白名单四条收窄手段全部失效（字母表置换权 + "白名单=新字母表"），
确认 base26 是**真下限**，无法确定性区分。base36/62（含数字）、base52（大小写混写）、
base33/43/59（含强符号）、base27/28/11（含下划线）、base>94 非 ASCII（含单码点/不可打印）、

#### 8.2.1.16 ASCII 锚 + 非 ASCII 字母表：值/键规则不对称（V18 对抗复核）

第十八轮对抗复核判定 **REFUTED**（规则层）：V17 的"投影为空⇒fail-closed"只拦 `t==""`
（投影**全空**），漏掉"**前缀 1 个 ASCII 字符 + 非 ASCII 编码**"——投影 `t` 变为单个
ASCII 字符（`len==1`），既非空、又不触发任何 `len>=2` 形状子句。而键循环有 `len==1`
兜底、值循环没有，**值/键两侧规则不对称**是直接根因：

| 缺口 | 根因 | 修复 |
|------|------|------|
| ASCII 锚 + 非 ASCII 字母表（`{"event":"aββα…"}`，`a` 为锚、`β/α` 为 base2 希腊字母表） | `t="a"`(len 1) 非空，`if not t` 不触发，`2<=len<=12` 也够不着 | 值循环改 `raw != t`（含**任一**非可打印 ASCII 字符即 fail-closed），与键循环对称 |
| 锚 + 空白/码点编码、锚 + 非 ASCII 键名（`abβ`/`a中`） | 同一投影错位，键侧 `len==1` 兜底只盖 1 字符 ASCII 前缀 | 键循环同样改 `raw_k != t`（含任一非可打印 ASCII 字符即 fail-closed） |

**纪律二十四：投影外内容检测要覆盖"部分落在投影外"，而非只覆盖"全部落在投影外"**——
"投影为空"只是"投影有损"的特例。正确的判据是 `raw != t`（原始载荷是否**含**投影外字符），
而不是 `t == ""`（投影是否**全空**）。这补上了纪律二十三在"部分投影外"这个中间地带的缺口。

**已知残余（信息论下限，诚实声明，不变）**：base26 **纯单大小写字母**片段拆片
（`{"bsr":"mvlim"}`）——与描述性词 `event/ts/ok` 信息论同构，确认为真下限。所有含
非可打印 ASCII 字符（空白/控制/非 ASCII）、含符号/下划线/数字的片段均已被覆盖。

#### 8.2.1.17 纯零宽字母表：`_ZW_RE` 预剥导致"投影外检测"前失明（V19 对抗复核）

第十九轮对抗复核判定 **REFUTED**（规则层）：V18 的 `raw != t` 修复在**原始串上**判
"含投影外字符"，但实现里先执行了 `raw = _ZW_RE.sub("", str(v))` 把 6 个零宽/软连字符

| 缺口 | 根因 | 修复 |
|------|------|------|
| 纯零宽字母表（base2/4/6，用 `\u200b` 等 6 个零宽字符编码 PII） | `_ZW_RE.sub` 先把零宽剥成空 → `continue` 跳过，连"投影外内容"检查都走不到；`_value_pii_shapes` 的 `_text_variants`/`_digit_extract` 同样先剥零宽 ⇒ 值级形态层同时失明（交叉盲区） | ⑥ 直接判 `v_str != t`（在原始串上，不预剥零宽），零宽是 `[!-~]` 之外的字符 ⇒ 自然触发 |
| 零宽夹带 / 零宽键名 | 同一 `_ZW_RE` 预剥 | 同上 |

**纪律二十五：检测前不要"预归一化"掉任何可能是信息载体的字符**——零宽字符视觉不可见、
在合法数据中**零出现**，是纯编码载体。归一化（`_ZW_RE`/`_fold_digits`）用于**形态匹配**
